# 运行模式与对话策略

模式由 `viktor/profiles.py` 中三张正交表组合：**提示词**决定行为，**限制**决定输出 token、工具轮次和 ptc 预算，
**工具白名单**决定模型能看到并调用哪些工具。模型与思考参数的具体映射见[会话、上下文与模型](conversation.md)。

## 1. 模式总览

| 模式 | 思考强度默认值 | 数值预算 | 主要工具权限 | 进入/离开方式 |
|---|---|---|---|---|
| `normal` 普通 | low | quick | 无建造写入工具 | 默认；可切 creative/creative_max |
| `creative` 创造 | high | heavy | 全量，含建造引擎与 pin_region | normal ↔ creative；也可到 creative_max |
| `creative_max` 创造 max | max | heavy ×2 | 全量 | 仅在玩家明确要求最高规格时使用 |
| `plan` 计划 | high | heavy ×2 | 禁止服务器指令、pin_region 和建造提交路径 | 仅控制词“计划模式”进入；模型可切 execute |
| `execute` 执行 | high | heavy ×2 | 可执行服务器指令与 pin_region；**无建造引擎工具** | plan → execute；本回合结束自动回 normal |
| `oneshot` 一次性 | low | oneshot | 确定性工具白名单 | 仅 `1 ...` 触发；无 set_mode |

`creative` 适合认真设计和施工；`creative_max` 只在“最好/最强/最大/max/不惜代价”等明确最高规格请求下使用，
更慢且成本更高。不要把玩家普通的“做大一点”自动等同于 max。

思考强度只是模式输出的 low/high/max 逻辑档位，实际请求字段（如 `effort` 或 `reasoning_effort`）由当前模型档案决定。

## 2. `set_mode` 与模式注记

模型调用 `set_mode(mode, reason?)` 切换模式。程序按当前模式的 `next_modes` 动态填充 `mode.enum`：

- normal ↔ creative / creative_max；
- creative ↔ creative_max；
- plan → execute；
- execute → normal；
- oneshot 没有 `set_mode`。

因此模型不能通过 `set_mode` 进入 plan 或 oneshot，未列出的目标也不会出现在 schema 中。计划模式的进入和退出只由
“计划模式”/“退出计划”控制词处理。

每次切换会在工具响应之后追加一条模式注记，包含当前模式、行为提示词及刷新后的 ptc/输出上限。
它只追加到日志尾部，不重写 system prompt，也不破坏已有前缀缓存。

交互模式的注记不明示工具轮次数字；一次性模式没有补救机会，因此会明确提示轮次上限。
`reasoning_content` 只写运行日志，不作为普通聊天正文展示。

## 3. 工具轮次用尽后的收尾汇报

交互任务达到工具轮次上限时，程序不替模型编造总结，而是追加系统注记并给予一次**无工具**收尾请求：

- 请求设置 `no_tools`，模型只能用正文汇报“已完成什么 + 下一步计划”；
- `_wrap_up_reply()` / `_finish_turn` 把内容播报并写回上下文；
- 引导玩家回复“继续”或给出调整，形成一次停下核对；
- 只有收尾 API 本身失败时，才使用程序兜底消息，避免沉默。

轮次预算有三条重要规则：

1. `round_cap` 取本轮曾使用过的最高模式上限，只增不减。创造模式做完后切回普通，不会因较低上限被倒扣成超限。
2. 任务运行中，在安全点注入新玩家消息后，`rounds` 归零，`round_cap` 重置为当前模式上限；插话视为新任务预算。
3. 一次性对话没有插话和“继续”流程，也没有收尾机会，轮次上限始终是硬顶。

## 4. 计划模式 / 执行模式

### 4.1 进入计划

任何玩家单独发送 **`计划模式`**（完全匹配）：

- 程序切到 plan，不重置上下文，因此可利用此前讨论和建造记录；
- 回复“已切换到计划模式，发送「退出计划」可退出计划模式”；
- nudge 一次，让 Agent 主动引导玩家规划。

计划提示词要求方案精确到坐标：范围、基准点、材料、步骤顺序和验收标准，并明确执行周期有限，过大工程必须分阶段。
计划阶段不能执行服务器指令、设置常加载或提交建造；查询、说话、记忆、技能、ptc 与允许的 set_mode 仍可使用。
只读预览/渲染能力以 `profiles.TOOLS` 的实际白名单为准，不应把“能生成预览”理解为“能修改世界”。

### 4.2 定稿与执行

方案经玩家确认后，模型调用 `set_mode("execute")`。execute 与 plan 共用 heavy ×2 数值限制，但换成执行提示词，
开放服务器指令与 pin_region；当前版本不向 execute 暴露 `build_*` / `render_build` / `build_blueprint`。

执行是一次性周期：本回合完成、停止或出错后，程序自动回 normal，不依赖模型主动切回。
任何玩家发送 **`退出计划`** 可从 plan 直接回 normal。

## 5. 一次性对话（`1 ...`）

玩家消息以 `1 ` 开头（数字 1 + 空格；也兼容全角空格），或单独发送 `1`，进入一次性对话。单独 `1` 会提示补内容。

- **隔离**：不进主对话，不唤醒或清空主会话；触发词、工具往返和结果单独写入 `logs/oneshot/`。
- **闭式完成**：一次“下达指令 → 多步工具 → 回报”，不能中途向玩家提问，也没有继续/收尾流程。
- **多步但确定性**：可先查坐标再执行指令再回报；不做开放设计、大规模施工、模式切换或常加载。
- **模糊请求**：无法判断时只说明缺少哪些关键细节，请玩家补充后重新发送，并提醒这是一次性对话。
- **并发**：主任务运行中也可触发，默认最多 4 个一次性对话（`oneshot_max_concurrent`）。API 请求可并行，
  共用控制台/日志的工具执行按门控串行，避免互相抢回包。
- **停止**：`1 强制停止` 停止全部一次性对话；没有 `1 停止`。裸“停止/强制停止”只作用于主对话。
- **模型**：始终使用默认模型 `flash`，不继承主会话的 Kimi 等模型，也不能在一次性对话中切换。
- **白名单**：不含 pin_region、set_mode、stay_silent 和建造工具；执行层再做一次黑名单校验，防止 ptc 夹带。

相关配置：`oneshot_effort`、`oneshot_max_reply_tokens`、`oneshot_max_tool_rounds`、`oneshot_max_concurrent`。

## 6. 静默消息（`0 ...`）

以 `0 ` 开头（也兼容全角空格）或单独一个 `0` 的消息只在游戏中给玩家看，程序直接丢弃：

- 不排队、不调用模型、不进主对话或任何上下文文件；
- 不触发 0→1 会话初始化，完全无状态；
- 不发 `[系统]` 或 `<维克托>` 回执。

适合玩家之间聊天或不希望 Bot 插嘴的内容。`0` 前缀仍会被其他玩家看到；`0x`、`0号矿洞在哪` 不匹配静默规则，
会按普通聊天处理。想对 Bot 说话不要加此前缀。

## 7. 该不该接话

普通聊天不做硬编码关键词回复，每条都交给模型判断 `send_chat_message` 或 `stay_silent`。
提示词按以下顺序命中即停：

1. **明确叫 Bot → 必须接**：名字/称呼、向服务器提问求助、下指令或只有 Bot 能做的事。
2. **正在对话 → 默认接**：Bot 刚对该玩家说过话（默认 3 分钟内）时，后续短答、补充、纠正和追加条件都视为接着聊；
   只有明显转向别人时才沉默。
3. **不在对话且没叫 Bot → 默认沉默**：玩家间约事、报坐标、分工和吐槽不插话，也不发“嗯/我在”占位。
4. **拿不准 → 沉默**：唯一例外是只有一名玩家在线，且明显正在等待回复。

程序每回合开头追加一条对话状态注记，避免模型从长上下文猜时间：

```text
# 对话状态(系统记录; 以最新一条为准, 不要回应这条注记)
- 这句话来自: Tester; 当前在线 2 人: Tester, Bob
- 你对 Tester 最后一次发言: 12 秒前, 那次有提问
- 你和说话的玩家之间没有正在进行的对话: 没明确叫你时保持沉默。
```

对话状态规则：

- 记录 `玩家 → (上次发言时间, 那一轮是否提问)`，从实际 `send_chat_message`（含 ptc 内嵌）文本计算。
- 提问按问号及“吗/呢”等结尾判断；先提问后报进度仍算有提问。
- 对某玩家的消息保持沉默会断开连续对话；清空/新会话会清空状态。
- 超过 `chat_dialog_window_sec`（默认 180 秒）的旧记录会标注超时。
- 恢复会话时从历史找最近发言对象，并以文件 mtime 作为时间基准，避免直接误判为持续对话。

## 8. 任务中插话

Agent 多轮任务执行期间收到的新消息，会在工具往返闭合后的安全点注入当前工作循环，而不是另起一轮：

- worker 开轮或安全点统一写入，保证 `assistant(tool_calls)` 与 `tool` 严格成对；
- 模型下一轮即可调整方向、纠错或补充条件，无需等整个任务结束；
- 新消息可能只是玩家间闲聊，模型自行判断：相关就调整，无关就继续原任务；
- 注入时即消费，不再重复排队；注入后按新任务重置工具轮次预算。

控制词不进入上下文，避免多线程追加时插入工具序列。
